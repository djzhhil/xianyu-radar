# 补货与扩充商品：现状评估和迭代计划

日期：2026-10-02。范围：评估现有实现，安排后续迭代；本文不代表相关功能已经实现。

## 1. 项目背景和目标

最初售卖电子资料的效果一般，后来从 X 上发现 FDE 资料并尝试售卖，获得了正向反馈。随后参考售卖同一份资料的商家，发现其他商品，再自行收集资料、整理并上架，也有商品能卖动。

项目要支持这条已经尝试过的路径：

**已验证商品 → 相关商家 → 商家全部商品及变化 → 我还没卖的相关商品 → 收集和整理 → 试卖 → 成交复盘。**

工具需要帮助回答三个问题：商家在卖什么；哪些商品我有能力补充；哪些尝试带来了新的有效商品。采集数量是过程指标，新增能卖动的商品才是结果指标。

暂按单人使用、闲鱼商家监控、按需手动扫描设计。用户已确认主题为 FDE，并有独立自动发货系统保存售卖数据，但尚未专门整理商品和成交清单。优先通过该系统的脱敏导出建立自有商品与成交记录；FDE 的具体主题边界、导出字段和统计口径仍待样本确认，不预设分类词典、销量或收益目标。

## 2. 当前能力和不足

以下判断以当前代码为依据；早期设计文档中的计划不能视为已实现功能。

| 能力 | 当前实现 | 对补货的影响 |
| --- | --- | --- |
| 发现商家 | 关键词搜索、分页、卖家识别、入池、诊断和恢复进度 | 可以从已验证商品寻找相关商家 |
| 商家管理 | 查看商家、切换监控状态、查看已存商品及事件 | 可人工核对商品；还缺主动添加已知商家、标签和备注 |
| 店铺扫描 | 完整目录、快照、上新/价格/标题/下架事件 | 已具备监控基础；分页不完整和商品骤减有保护 |
| 候选来源 | 仅非基线的上新；标题命中来源关键词会跳过 | 首次看到的存量商品不会入候选；相关新品可能被误排除 |
| 商品图片 | 解析器读取主图 URL，商品持久化未保存 | 重启后无法使用已采集主图做研究和对比 |
| 商品详情 | 发现阶段有用于补全卖家 ID 的详情请求 | 没有供选品研究使用的完整文案、图集和详情历史 |
| 商品聚合 | 标题转小写、去空白和部分标点后聚合 | 异名同物可能分开；同名不同版本可能误合并 |
| 候选评分 | 商家数和出现次数的简单组合 | 只能作为发现线索；不是销量、需求或利润评分 |
| 人工审核 | `new/watching/testing/validated/rejected` 状态 | 有流程框架，缺少理由、资料来源和试卖结果 |
| 我的商品和经营数据 | 本项目暂无；独立自动发货系统已有售卖数据 | 可从既有系统导入，不必从零逐条整理；需确认商品与订单字段 |

主要代码依据：

- `src/xianyu_radar/modules/scan/service.py`：首次成功扫描的基线判断和目录写入。
- `src/xianyu_radar/modules/scan/candidate_detector.py`：跳过基线和关键词命中项、标题归一化及评分。
- `src/xianyu_radar/modules/scan/shop_parser.py`、`item_repository.py`、`history.py`：主图解析与当前保存字段之间的缺口。
- `src/xianyu_radar/modules/pool/service.py`、`entrypoints/api/routes/pool.py`：当前商家管理入口。
- `src/xianyu_radar/modules/candidates/service.py`、`repository.py`：审核状态及候选查询。

代码和现有文档表明，采集已有诊断和可靠性修复，也做过限定范围在线验收；本次未使用真实登录态发起请求，不能据此保证所有商家和详情字段在线可用。

## 3. 调整选品规则

### 存量商品和上新分别处理

首次完整扫描继续作为监控基线，不制造假上新。但允许人工从完整存量目录加入研究候选，并注明 `baseline_catalog` 来源；后续真实上新注明 `new_item`。已有目录可复用，避免为了候选转换重新抓取。

新老来源都遵守目录质量门槛。旧候选的 `legacy_unverified` 标记继续保留，不能因为进入新流程就变为可信记录。

### 搜索关键词和排除规则分别配置

来源关键词用于发现商家，不自动代表“我已经售卖的商品”。相关性、是否已售、是否值得尝试应分别记录。

对 FDE 相关商品支持“相关 / 不相关 / 待判断”，先由人工确认。是否已售通过自有商品清单和明确映射判断；不确定的匹配交给人工复核。不同版本、年份、语言和套餐应保留差异，避免只按标题合并。

### 保留判断依据

一个候选可以关联多个实际商品和商家，每条来源保留商品 ID、链接、价格、观察时间和来源类型。标题聚合只提出建议，允许人工合并和拆分，不能覆盖来源记录。

多商家售卖、反复上架和价格变化是线索，不等于成交。现有 `appearance_count` 也不是每天仍在售的次数；如需分析持续在售时间，应根据完整扫描记录另行计算。

## 4. 按阶段实施

阶段按照依赖推进，不预先承诺工期。每个阶段都先完成可验收的小功能，再决定是否继续扩大。

### 阶段 A：补齐商家目录和存量选品（最高优先级）

交付：

1. 已知商家手动入池，支持可确认的数字 seller ID 和受支持的主页链接；去重，记录手动来源、备注和标签。
2. 商家商品目录增加标题搜索、在售/下架筛选、最近扫描时间和目录质量提示。
3. 保存扫描已取得的主图 URL；新增缩略图展示，旧商品无图时显示缺失，不伪造历史图片。
4. 完整存量目录支持勾选加入研究候选；候选保留存量与上新来源区别。
5. 将来源关键词与明确排除条件分开；提供筛选命中理由和人工复核入口。

验收：选一位已知商家，完成入池和完整扫描；人工核对目录；选取其存量商品加入候选且不产生假上新。重复操作不重复建来源；分页失败时不得用半份目录替换当前态，也不得自动产生可信候选。

### 阶段 B：识别我还没卖的商品，形成补货清单

交付：

1. 优先导入自动发货系统的商品导出，支持 CSV 和手动补充：来源系统商品 ID、商品名、版本、主题、自己的商品链接、在售状态和备注。先确认真实字段再实现适配；重复导入按来源 ID 更新，不重复建商品。
2. 候选与自有商品手动关联，区分已售、未售、待核对；允许一对多版本关系。
3. 增加资料能否获得、整理工作量、预期上架价格、尝试理由和拒绝理由。
4. 记录候选审核历史，输出可下载的补货清单：候选、来源、差异、下一步、阻碍和状态。

验收：录入一批真实在售商品，对照商家目录，人工确定至少一批“还没卖、值得研究”的商品；已售和未确认项能分开查看，每个补货条目都有来源和下一步。数量目标在提供实际清单后约定。

### 阶段 C：按需采集商品详情和研究素材

交付：

1. 从候选或商品页手动触发详情采集，先做单商品，再做有数量上限的勾选批次。
2. 保存实际返回的标题、完整描述、图集 URL、价格、来源链接和采集时间；字段缺失显示未取得。
3. 详情采集有独立状态、错误原因和恢复入口；缓存已有详情，验证或限流后停止后续请求。
4. 增加内容版本和变化比较；按需下载图片到本地，记录来源、文件校验值及单图成功/失败结果。
5. 导出研究包，包含字段清单、文案、成功取得的图片和来源记录，方便分析商品表达和套餐差异。

范围：采集商品页面展示的图片和文案。卖家实际交付的电子资料不是商品页面素材，不能把“取得页面详情”当成“已取得可售资料”；另外记录自行收集的内容来源和使用条件。

验收：小批样本人工对照页面，字段完整或明确标缺失；重试不丢旧版本，单图失败不使其他成功素材丢失；遇到验证后批次停止，目录扫描和已有候选仍可用。

### 阶段 D：试卖和复盘

交付：

1. 候选关联自己的上架商品和试卖批次，记录开始/结束时间、价格、整理耗时及投入。
2. 优先导入自动发货系统的订单记录，以来源订单 ID 去重，并映射商品、时间、金额和状态；区分付款、发货、退款等实际可取得的状态，发货次数不能直接当成订单数。咨询数、直接成本和维护耗时等系统缺失信息由手动补充，未记录的值保持缺失，不当作零。
3. `validated` 有明确验证依据和日期；区分试卖中、没有有效结果、有效商品，保留失败理由。
4. 按主题、来源商家和试卖批次复盘，展示哪些来源带来了自己的有效商品。

验收：至少完成一个真实试卖批次，能追溯“来源商品 → 候选判断 → 自行收集 → 我的上架 → 结果”。观测周期和成功条件由自己的经营情况确定，不能仅靠修改审核状态认定成功。

## 5. 指标和复盘方法

| 层次 | 记录什么 | 用来决定什么 |
| --- | --- | --- |
| 采集质量 | 完整扫描比例、覆盖商家、失败原因、最近成功扫描时间 | 当前数据是否足够支持判断 |
| 选品效率 | 复核商品数、未售相关商品数、选品和整理耗时 | 工具有没有减少重复查找和无效工作 |
| 补货结果 | 实际上架数、实际成交商品数、退款、收入和投入 | 扩品是否有效，哪些方向值得继续 |
| 来源价值 | 各商家带来的候选、试卖和有效商品数 | 哪些商家值得重点观察 |

试卖转化率按“有成交的试卖商品数 / 已完成约定观测期的试卖商品数”计算，并显示样本数和缺失数据。尚在观察的商品不记为失败。收入减直接成本可单列，但没有完整成本时不声称是净利润。

每完成一个试卖批次，回看：哪些线索带来结果；哪些资料难以收集；哪些同类商品只是重复；哪个步骤最耗时。根据实际瓶颈决定下一步功能，不用采集总量代替业务结果。

## 6. 实现边界和验证

- 沿用现有 Python、FastAPI、SQLite 和 Web 页面，不为该计划重建技术栈。
- 商家管理沿 `API/CLI → pool.service → 公共 seller_repository` 扩展；扫描字段沿 `scan → 自有存储` 扩展。
- 候选来源、自有商品关联和审核由明确的业务入口负责；模块不直接导入其他模块的内部函数。共享持久化契约放到公共基础组件。
- 详情采集独立于完整目录扫描；不得让单商品详情失败影响目录质量判断或触发下架。
- 数据库变更用版本迁移并备份，保留旧候选和人工审核结果；新增字段和回填策略单独验收。
- 回归重点覆盖基线不造假上新、重复来源去重、关键词规则、失败目录保护、详情部分失败和旧数据迁移；有页面改动时补充实际交互验证。
- 在线验证每阶段使用事先选定的小样本；继续按需扫描，不因启动 Web 服务启动 `radar run`。
- 自动上架、全店无差别详情下载、AI 热销预测和多账号调度暂缓，待试卖闭环的数据说明它们有价值后再评估。

## 7. 下一步建议和待补充信息

先做阶段 A，再做阶段 B；它们最直接解决“这些商家现在有什么，以及我还缺什么”。阶段 C 在有具体候选需要深入分析时推进；阶段 D 的记录字段可提前确定，以免试卖后缺少结果数据。

下一份有用的输入是自动发货系统的脱敏导出样本，不必先手工整理全量数据：商品表和订单表各提供少量记录及字段名即可。商品表优先包含商品 ID、名称、在售状态和链接；订单表优先包含稳定订单 ID、商品 ID、订单时间、实付金额及付款/退款状态。导出实际有哪些字段就保留哪些，不要求系统具备全部字段。无需买家姓名、手机号、地址、聊天记录、账号凭据或资料下载密钥。

仍需补充：FDE 的具体主题和商品版本差异；重点商家及店铺链接；导出字段与成交口径；平时整理一份资料的投入；资料抓取优先需要哪些字段。缺少这些信息不妨碍完善目录能力，但会影响相关性规则、试卖目标和功能排序的细化。
