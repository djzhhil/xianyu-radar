# 正式部署方案

确定时间：2026-10-03。本次正式上线采用**固定 Git 提交的完整源码部署**，独立虚拟环境安装，由 systemd 管理服务。本文确定发布方式，不执行生产部署。

## 发布单元与目录

每个版本使用已验证并合并到 main 的完整提交 SHA。导出完整跟踪源码，必须包含 `src/`、`web/`、`pyproject.toml`、README 和数据库迁移文件。发布目录禁止直接编辑或滚动 `git pull`；修正必须作为新提交重新检查、发布。

目标目录约定如下（上线时由运维创建，与当前开发工作区分离）：

```text
/srv/xianyu-radar/
  releases/<commit-sha>/       # 完整源码，含 web/ 和该版本的 .venv/
    data -> ../../shared/data
  current -> releases/<commit-sha>
  shared/data/                # 持久化业务数据库、旧用户文件及调试目录
/etc/xianyu-radar/helper.env   # Helper 服务端配置，限制文件访问权限
```

当前 `config.py` 根据源码位置确定根目录和 `data/`，因此每个发布目录必须将 `data` 指向同一持久化目录。不可把开发数据库打进发布物，也不可用新版本空目录覆盖生产数据。现有旧 Cookie 文件保留，在线流程不读取它们。

在每个发布目录创建独立 `.venv`，使用 Python 3.12（本次回归环境），安装源码 `pip install -e .`；运行依赖版本须与验收环境一致，依赖升级单独验证。生产环境无需安装测试依赖，不使用 `--reload`。当前 wheel/sdist 不包含 Web 静态资源，不能用于完整 Web 服务部署；本次不新增容器构建流程。

## 服务运行

systemd 使用专用服务用户、`WorkingDirectory=/srv/xianyu-radar/current`，并从受保护的 `/etc/xianyu-radar/helper.env` 加载四项 `RADAR_HELPER_*` 配置。启动命令为：

```text
/srv/xianyu-radar/current/.venv/bin/radar-web --host 127.0.0.1 --port 8765
```

保持单个 Web 进程，使用现有账号串行锁。Helper 管理登录和闲鱼会话互相隔离。服务启动仅启动 Web/API，不启动 `radar run`，扫描继续按需手动执行。

当前 Web 没有远程访问鉴权并限制回环监听。远程访问必须通过具备认证与 HTTPS 的反向代理，或 SSH 隧道；仅增加普通转发代理不足以公开访问。生产日志不记录 Cookie、Helper 密码或原始凭证版本。

## 首次上线与后续更新

1. 选择通过发布检查的提交，生成完整源码目录并安装该版本独立虚拟环境；核对 `web/` 和迁移文件齐全。先在临时数据目录完成验收，避免接触生产数据库。
2. 配置 Helper 根地址、用户名、密码、目标账号 ID，确认运行中的 Helper 支持交换接口，账号归属及已有续期条件满足。
3. 首次迁移时停止旧服务及所有业务写入，备份现有 SQLite 数据库，并将原数据保留在共享目录。已有目标数据库时核对来源，不覆盖或删除。后续升级继续复用共享目录。
4. 停止 Web 及正在执行的手动操作，完成一致性数据库备份。用候选版本的 `radar init-db` 应用必要迁移，确认成功，再切换 `current` 并启动服务。
5. 检查服务、静态界面、业务数据库及 Helper 状态，完成搜索、商品详情、商家商品列表的真实请求与响应 Cookie 回写验证，确认版本推进和 `runtime_sync_status`。全部通过后记录提交 SHA、依赖版本、备份位置与验收结果。

当前尚未配置真实 Helper 连接参数，因此真实联调仍是上线前条件。源码、离线测试通过不代替目标环境验收。

## 回滚

保留上一版本源码和虚拟环境。遇到发布故障先停止服务与业务写入；确认数据库结构与旧版本兼容后，将 `current` 切回上一提交并重启、验证。数据库迁移后的回滚必须先评估兼容性；不要自动恢复旧数据库覆盖上线后新增业务数据。必要的数据恢复需另行确定方案。

本次结论为源码部署。容器化或独立安装包可作为后续任务；若改用这些方式，应先补齐静态资源打包、独立持久化路径及部署验收。
