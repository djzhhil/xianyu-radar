# 下一阶段计划书：从商家目录到补货清单

日期：2026-10-02。状态：T1 商家目录、前端工作台重构和 T2 候选来源/选品/规则已完成并验证；T3–T5 未实施，T0 真实业务导出样本待补充。分支和验证记录见 `PROGRESS.md`。

本文将 `replenishment_plan.md` 的阶段 A、B 拆成下一轮可执行任务。数据要求见 `next_phase_data_requirements.md`。

## 1. 目标与交付结果

围绕 FDE 相关商品，建立一个能回答“商家有什么、我已经卖什么、下一批值得补什么”的工作流程。

完成后，可以主动添加已知商家，查看其完整商品目录及主图，把存量或上新商品放入候选，对照自己的商品清单，记录补货理由，导出待处理清单。

本阶段成功的标准是能产出一批可追溯、经人工确认的补货条目。实际新增有效商品需要后续上架和成交观察，本阶段不把候选数量当作销售成果。

## 2. 范围

| 本阶段交付 | 交付边界 |
| --- | --- |
| 已知商家入池 | 数字 seller ID、明确支持的主页链接、备注和标签；重复添加不重复建来源 |
| 商家商品目录 | 分页、标题搜索、状态筛选、主图、最近完整扫描和失败提示 |
| 存量商品选品 | 完整扫描的存量可人工加入候选，与后续上新来源分开记录 |
| 筛选规则调整 | 来源关键词不再直接代表排除商品；独立排除规则和命中理由 |
| 自有商品对照 | 导入自动发货系统的商品清单，人工确认关联和版本差异 |
| 补货清单 | 理由、可获得性、整理投入、下一步、审核历史和 CSV 导出 |
| 售卖数据准备 | 确认订单字段、去重键和成交口径；用脱敏样本核对，不强行生成销量 |

完整描述、图集下载、自动上架、自动同步生产数据库和经营分析看板不在本阶段交付范围内。保持按需手动扫描。

## 3. 实施顺序与验收

### T0：确认业务样本与数据契约

输入：重点商家、自己已售商品样本、自动发货系统只读探查结果和导出样本。初步探查已确认 PostgreSQL 中存在 `item_info` 与 `orders`，具体字段见数据需求文档；无需从发货日志推测是否有商品和订单表。

交付：字段映射、商品身份规则、订单状态解释、FDE 的版本区分和一组人工核对样本。确认“自动发货配置中的商品”是否就是“实际在售商品”，不能默认二者一致。

验收：每个必要字段明确来源、可否为空、缺失时怎么处理；能关联的商品和不能关联的商品分别有结论。重点核对 `(cookie_id,item_id)` 关联、软删除、多规格、文本金额和无时区时间。若远程连接不可用，记录原因，采用用户导出样本；T1–T2 可以先推进。

### T1：主动添加商家并完善目录

沿 `pool` 入口增加手动入池、备注和标签；完善目录查询。沿扫描解析和持久化链路保存主图 URL，展示最近可信目录及其采集时间。

验收：同一商家重复添加只有一条有效手动来源；原有暂停状态不因重复添加被悄悄解除。搜索和状态筛选影响正确的分页总量。旧商品无图有明确缺失状态，新图扫描后可显示。不完整扫描保留上一份可信目录并展示失败信息。

### T2：补齐候选来源，调整筛选规则

增加候选商品来源记录，至少保存候选 ID、商品 ID、卖家 ID、来源类型、首次加入时间和依据扫描 ID。完整存量可人工加入候选；真实上新继续来自监控事件。

将来源关键词和独立排除规则分开，默认不因关键词命中自动跳过相关新品。存量初始以人工选择为主，避免一次生成大量未经复核候选。

验收：首次扫描不产生假上新，但存量可以进入候选；重复加入同一来源不重复计数。分页失败和未核实历史来源不能伪装成可信来源。FDE 相关上新不会仅因搜索关键词命中而被跳过。回归检查旧状态、来源商家数和历史质量标记。

旧候选只有商家关联和样例商品，无法据此还原所有历史商品来源；迁移保留已有记录和不确定性，不虚构缺失证据。

### T3：导入自己的商品并对照候选

新增自有商品能力：来源系统、稳定商品 ID、名称、规格/版本、在售状态、平台链接和导入批次。先支持 CSV；真实导出若为 JSON，再按样本增加适配。

导入先预览字段映射、有效行、无效行和变更摘要，确认后写入本项目数据库。按来源系统和稳定 ID 去重，允许人工补充信息。名称匹配只做建议，最终关系人工确认。

验收：同一文件重复导入不增加商品数；更新导入不会抹掉人工备注。空状态不当作在售，名称相似不直接认定相同商品。候选可以显示“已覆盖 / 未覆盖 / 待核对”，但只有人工确认的对应版本才记为已覆盖。

### T4：形成可执行的补货清单

候选新增相关性、是否已有、资料可获得性、整理投入、预期上架价格、决策理由和下一步。记录审核前后状态、时间和理由，避免只有一个最终标签。

清单展示商品、来源商家与链接、已有商品关联、版本差异、审核结论和下一步；支持筛选与 CSV 导出。单价只是参考报价，不作为收益预测。

验收：每个决定尝试的条目有来源和理由；已售、拒绝、待核对项可分别查看；导出与当前筛选结果一致，并保留稳定 ID。测试导出中的逗号、换行和表格公式样式文本，避免字段错位或被表格软件当公式执行。

### T5：端到端小批验收与交接

建议试点规模：3–5 位已知商家、10–20 个自有商品样本、人工复核约 20 个商家商品。它们是启动规模，不是必须凑满的业绩指标；实际商品不足时缩小样本并说明覆盖范围。

验收路径：添加商家 → 完整扫描 → 选择存量与上新 → 导入自有商品 → 人工对照 → 输出补货清单。

测试覆盖正常数据、重复操作、不完整扫描、缺失图片、旧候选迁移、重复导入和版本歧义。有页面改动时检查实际桌面和移动交互。在线测试限于选定样本，遇到验证或限流即停止。

交付使用记录、已知限制和下一轮建议。若没有合适候选，保留原因，不为了数量降低选品标准。

## 4. 依赖和工程安排

依赖关系：`T0 → T3 → T4 → T5`；`T1 → T2 → T4`。售卖数据样本暂缺时，先完成目录和候选能力，再用人工商品清单验收导入框架。

| 改动链路 | 主要位置 |
| --- | --- |
| 商家与目录 | `entrypoints/api/routes/pool.py` → `modules/pool/service.py` → 公共卖家存储 |
| 图片和可信目录 | `modules/scan/shop_parser.py` → `item_repository.py`、`history.py`及版本迁移 |
| 候选来源与审核 | 候选 API、`modules/candidates` 和扫描持久化契约 |
| 自有商品与导入 | 新增职责明确的自有商品模块，通过公共存储契约与候选关联 |
| 展示和导出 | 沿现有 Web 页面和 API 扩展，不重建框架 |

任务各用独立 `codex/` 分支；修改前检查工作区，验证通过后提交、检查差异并合并 `main`。模块不直接调用其他模块内部函数。数据库升级先备份，保存旧审核状态；新增流程应可关闭，失败迁移不得继续写业务数据。

本阶段按 T0–T5 顺序评审完成情况，不承诺未经样本验证的工期。T0 完成后，再依据导出格式、商品映射难度和页面范围给出工作量估计。

## 5. 现有业务系统的只读边界

对 `10.0.0.8` 的授权是初步只读探查。查看现有部署结构、应用中数据定义、可用导出入口和有限元数据；不修改文件、配置或数据库，不启停服务，不执行发货，不安装程序。

优先查看已有代码中的表结构和状态定义。确需数据库查询时使用只读连接、短时限和小结果集；SQLite 使用真正的只读模式，数据库有 WAL 时不忽略未检查点数据，也不使用可能遗漏数据的 `immutable` 假设。无法保证只读或查询成本时停止该路径。

探查不等于授权定时直连生产库。后续默认读取用户导出的文件或已有导出接口；任何新增生产侧接口、脚本或账号，另列变更方案后再执行。

## 6. 阶段结束时的判断

重点看三件事：是否减少逐店翻找时间，是否能准确区分已售和未售，是否产出自己愿意投入整理的商品。

若瓶颈是看不懂商品内容，下一阶段推进按需详情和图集；若瓶颈是判断投入是否值得，推进试卖记录与订单导入；若瓶颈是目录经常采不到，先改善采集稳定性。最终顺序以试点记录为依据。
